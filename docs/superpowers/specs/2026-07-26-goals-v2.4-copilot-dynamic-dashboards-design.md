# Goals v2.4: AI Copilot & Dynamic Dashboards — Design

**Date:** 2026-07-26
**Status:** Approved (design review with James, 2026-07-26)
**Builds on:** v1 goals spec (Goal/GoalMetric spine, MetricSource registry),
v2.0–v2.3 specs (connectors, benchmarks, assisted sources)

## Problem

The `/goals` first screen is a static template gallery, and the goal detail
page is a fixed stack of eight hand-ordered sections. Users who want to track
something that isn't one of the 20 templates — or that blends concepts from
two goal kinds ("grow demo bookings *and* the revenue they convert to") —
have no path except forcing it into `custom_kpi`. v2.4 adds an AI Copilot
that turns a natural-language goal description into a customized, persisted
dashboard, and rebuilds the tracking page as a widget engine so every goal —
Copilot-created or not — becomes dynamic.

## Decisions (settled in design review)

1. **Everything stays on the existing goal spine.** The Copilot creates a
   real `Goal` plus a widget layout — no new Dashboard entity, no ephemeral
   previews. Benchmarks, digests, ROI reports, and recommendations keep
   working unmodified.
2. **Copilot hero + gallery below.** The describe-your-goal input is the
   first thing on `/goals`; the 20-template gallery remains beneath it as the
   browsable alternative. Nothing existing is removed.
3. **A goal may have N metrics.** `GoalMetric` drops its one-per-goal
   uniqueness; exactly one metric is `primary` (drives progress/risk/pace
   exactly as today), the rest are `supporting` context series.
4. **One-shot draft + editable preview** — not multi-turn chat. One
   `generateStructured` call produces a full draft; gaps become inline
   fields on a live dashboard preview, not chat turns.
5. **Widget registry + validated layout JSON** — not LLM-free-form layout,
   not fixed presets. The Copilot composes from a closed widget vocabulary;
   the server re-validates every field of the draft against closed sets
   (7 kinds, registered sources, registered widget types). The model never
   writes to the database.

## Data model

### `GoalMetric` (modified)

- `@@unique([goalId])` → `@@index([goalId])`.
- New `role String @default("primary")` — `'primary' | 'supporting'`.
- New `label String?` — display name for the series ("Demo bookings");
  null falls back to the source's metric descriptor label.
- New `unit String?` — `'usd' | 'count' | 'percent'`; a supporting series
  may have a different unit than the goal (count of leads on a usd goal).
  Null means "inherit the goal's unit" (the v1 behavior; all existing rows).
- Migration adds a **partial unique index** (raw SQL, like the k-anon
  migrations): `UNIQUE (goal_id) WHERE role = 'primary'` — one primary per
  goal is enforced by the database, not just app code. Existing rows are
  backfilled `role = 'primary'`, which satisfies the index because they are
  unique on `goalId` today.

### `Goal` (modified)

- New `dashboardLayout Json?` — `{ version: 1, widgets: [{ id, type,
  config }] }`. `null` (all existing goals) means "render
  `defaultLayoutForGoal(goal)`", which reproduces today's detail-page
  section order per kind. No backfill needed.

### Unchanged semantics

- `evaluate.ts` computes progress/risk/pace from the **primary** metric's
  datapoint series only. Supporting series never affect risk transitions,
  recommendations, digests, periods, or benchmarks.
- `refresh.ts` syncs **all** metrics of a goal on their own
  `refreshIntervalHours`/`lastError` cadence (it already iterates
  `GoalMetric` rows, not goals; audit for any one-metric-per-goal
  assumptions).
- `MetricDatapoint` is untouched — already keyed by `goalMetricId`.

## Widget registry

`src/lib/goals/dashboard.ts` — widget type definitions, per-type zod config
schemas, layout schema (`parseDashboardLayout`), and
`defaultLayoutForGoal(goal)`. `src/components/goals/widgets/` — one
component per type, thin wrappers over the existing viz components.

| Type | Renders | Config | Origin |
| --- | --- | --- | --- |
| `kpi` | stat tile: current / target / progress / pace delta | `metricId?` (default primary), `variant` | new (extracted from GoalCard math) |
| `trend` | `GoalTrendChart`: actual + pace + projection | `metricId?` | refactor of "Trend and pace" |
| `progress` | `GoalProgressBar` with pace tick | — | refactor |
| `comparison` | 2+ series overlaid, each on its own normalized scale | `metricIds[]` | **new** |
| `ratio` | derived series: numerator ÷ denominator per `bucketKey` | `numeratorId`, `denominatorId`, `format` | **new** — the "goals not on the list" payoff (e.g. lead→revenue conversion) |
| `narrative` | the Copilot's rationale for this dashboard | `text` (static, stored) | **new** |
| `impact` | measured/estimated ROI tiles + correlation line | — | refactor of "Impact on this goal" |
| `benchmark` | k-anon "How teams like yours do" card | — | refactor |
| `periods` | recurring settlement pills | — | refactor |
| `contributions` | `ContributionPanel` | — | refactor |
| `history` | datapoint table + record-value dialog | `metricId?` | refactor of "Metric history" |
| `rollups` | child personal-goal list with risk badges (org goals only) | — | refactor of "Supporting personal goals" |

Rendering rules:

- Unknown widget type or config that fails its zod schema → widget is
  skipped (fail-soft), console-warned in dev. A layout that fails
  `parseDashboardLayout` entirely → fall back to the default layout.
- Widgets referencing a metric that no longer exists render an inline
  "series removed" placeholder, not a crash.
- `ratio` aligns the two series on `bucketKey` and skips buckets missing
  from either side; division by zero skips the bucket.
- `comparison` normalizes each series to its own min/max (no dual-axis
  lying) with per-series legend + latest value.
- Everything stays hand-rolled SVG on `chart-math.ts` — no chart library.

**Default layout parity:** `defaultLayoutForGoal` must reproduce the current
section order (periods → trend → impact → contributions → benchmark →
history, with periods only when recurring, rollups only for org goals) so
shipping the engine changes nothing visually for existing goals. A snapshot
test locks this.

## Copilot draft API

`POST /api/goals/copilot/draft`, body `{ description: string }` (≤ 2000
chars). Auth: session required, same org scoping as `/api/goals`.

Server assembles grounding context:

- The 7-kind vocabulary with labels, units, and direction defaults.
- The org's **available** metric sources (same availability computation as
  `GET /api/goals/metrics/sources`) with their metric descriptors.
- The template catalogue as few-shot examples of well-formed goals.

One `generateStructured` call on the existing `ModelRunner`
(`DEFAULT_AGENT_MODEL`, injectable `generate` for tests — the
`assisted-extraction.ts` pattern). Output schema:

```text
{
  name, description, kind, direction, unit, recurrence, scope,   // closed enums
  suggestedTarget: { value, rationale } | null,
  suggestedTargetDate: string (ISO date) | null,
  metrics: [ { label, role, source, metricKey, unit,
               config? (sheets range / sql / url per source) } ],  // 1–4
  widgets: [ { type, config } ],
  rationale: string
}
```

**Server-side re-validation (never trust the model):**

- `kind` ∉ the 7-kind enum → 422 (the whole draft is unusable).
- A metric whose `source` isn't currently available → replaced with
  `manual` + a validation note surfaced in the preview.
- Widget entries with unknown `type` or invalid config → dropped, noted.
- More than one `role: 'primary'` → first wins, rest demoted.
- Missing/empty widgets after validation → default layout for the kind.
- Target date in the past → cleared (preview requires the user to set one).

Response: `{ draft, notes: string[] }`. **No DB writes.** LLM error or
timeout → 502 with a friendly message; the client toasts and points at the
gallery/wizard.

## `POST /api/goals` (extended)

- Accepts optional `metrics: [...]` (validated: exactly one primary, ≤ 4
  total, sources from the zod enum) and `dashboardLayout` (validated by
  `parseDashboardLayout`).
- The existing single-metric payload continues to work unchanged (internally
  adapted to a one-element primary array) — the wizard and its tests are
  untouched.
- Baseline preview/verification applies to the **primary** metric exactly as
  today; supporting metrics sync on the first refresh cycle and may start
  empty.

## `/goals` first screen

New `GoalCopilot` hero component above the gallery:

- Large textarea, placeholder "Describe what you want to achieve…", 3–4
  example prompt chips (drawn from template names + one blended example).
- Submit → inline "Designing your dashboard…" state → the **preview**.
- Visibility: hidden when no LLM is configured (capabilities check), page
  degrades to exactly today's layout.

**Preview** (new client component, rendered in place of the hero after a
draft returns): the real widget renderer in a preview mode —

- Inline-editable: name, target value, target date, recurrence,
  org/personal, per-metric source picker + source config, reusing the
  wizard's source-config fields and `POST /api/goals/metrics/preview`
  baseline verification for the primary metric.
- Widgets without data render designed skeleton/sample states; verified
  preview values appear where sources resolve.
- Validation notes from the draft API display inline ("Stripe isn't
  connected — this series starts as manual").
- Actions: **Create dashboard** (POST `/api/goals` with metrics + layout →
  redirect to `/goals/[id]`), **Start over**, and **Open in wizard**
  (escape hatch: prefills `/goals/new` like templates do).

The template gallery and `/goals/new` wizard are unchanged.

## Goal detail page

`/goals/[id]` becomes `<GoalDashboard goal={...} layout={goal.dashboardLayout
?? defaultLayoutForGoal(goal)} />` — the PageHeader, edit/archive dialogs,
and data fetching stay; the section stack is replaced by the renderer.

**Edit dashboard** (lean v1): a dialog listing registry widgets with
add/remove checkboxes and up/down reordering; per-widget config limited to
picking the metric for `trend`/`history`/`kpi`. Saves via `PATCH
/api/goals/[id]` (`dashboardLayout` added to its zod schema). No
drag-and-drop grid.

`GET /api/goals/[id]` response gains `metrics: [...]` (all series with
label, role, unit, datapoints) while keeping the existing primary-metric
fields for back-compat.

## Errors & fallbacks

| Failure | Behavior |
| --- | --- |
| LLM unavailable/timeout at draft | Toast + steer to gallery/wizard; hero stays usable for retry |
| Suggested source not connected | Series falls back to `manual`, inline note |
| Layout JSON invalid at render | Default layout |
| Widget config invalid | Widget skipped, others render |
| Referenced metric deleted | Inline placeholder in that widget |
| Ratio with missing/zero buckets | Bucket skipped |

## Testing

- **Unit:** layout zod schema (round-trip + hostile input), draft validator
  (bad kinds, unknown widgets, unavailable sources, duplicate primaries,
  past dates), `defaultLayoutForGoal` snapshot parity per kind, ratio
  alignment math (offset buckets, zero denominators), comparison
  normalization, multi-metric create/PATCH API validation,
  evaluate-uses-primary-only.
- **Route smoke** (per the `verify` skill, throwaway Postgres): copilot
  draft route with an injected fake `generate` returning a canned draft;
  goal create with `metrics[]` + layout; detail GET returning all series;
  refresh cycle syncing a supporting metric.
- **Regression:** existing goal, template, wizard, evaluator, and benchmark
  tests pass unchanged (the default-layout parity test is the guard).

## Out of scope (YAGNI)

- Multi-turn Copilot chat; drag-and-drop grid layout; a Dashboard entity
  spanning multiple goals; new metric-source adapters; auto-connecting
  integrations from the Copilot; LLM-suggested targets sourced from
  benchmarks (the rationale string is enough for v1).
