# Goals v2.0: Recurring Goals, Goal-Aware Prompts, Weekly Digest — Design

**Date:** 2026-07-26
**Status:** Approved (design review with James, 2026-07-26)
**Builds on:** `2026-07-25-goals-design.md` (v1, implemented on `feat/goals`)

## Problem

v1 goals are one-shot: a target and a date. Real targets are periodic (quarterly
quota, monthly MRR), the platform's agents and assistant are still goal-blind,
and nothing tends the garden — a user who doesn't open `/goals` never hears how
their goals are doing. v2.0 makes the platform feel goal-oriented daily.

## Decisions (settled in design review)

1. **Recurrence = sliding window over one Goal row**, not goal cloning. History
   lives in a new `GoalPeriod` table; datapoints, contributions, and the goal id
   stay continuous.
2. **Auto-renew.** A settled period opens the next one automatically with the
   same target (editable any time). No renewal prompts.
3. **Digest delivery: in-app notification + web push, AND email** via the
   built-in email integration. Email inherits the known single-tenant
   limitation (global env var) and no-ops gracefully when unconfigured.
4. Prompt grounding is a bounded text block (≤ ~600 chars, top 3 goals by risk
   severity) injected into the assistant, agent runs, and copilot grounding.
   A grounding failure degrades to an empty block — never breaks a run.

## Data model

### `Goal.recurrence` (new column)

`String?` — `'monthly' | 'quarterly' | 'yearly' | null` (null = one-shot, v1
behavior unchanged). Wizard defaults: quota → quarterly, mrr → monthly, all
other kinds → one-shot; always user-overridable.

### `GoalPeriod` (new model)

House conventions (cuid, org FK cascade, `@@map`, Timestamptz).

| Field | Type | Notes |
| --- | --- | --- |
| `goalId` / `organizationId` | FK cascade | |
| `periodStart`, `periodEnd` | Timestamptz | the window that settled (old `startAt`/`targetDate`) |
| `startValue`, `targetValue`, `finalValue` | Float | frozen at settlement; `finalValue` = last reading in the window (fallback: `startValue` when the window had no readings) |
| `outcome` | String | `'achieved' \| 'missed'` |
| `createdAt` | Timestamptz | |

Index `@@index([organizationId, goalId, periodEnd])`. Rows are immutable.
Org back-relation added for teardown completeness.

## Rollover

In `evaluateAndPersistGoal`'s settlement branch (`src/lib/goals/refresh.ts`):
when `now > targetDate` and `goal.recurrence` is set and status is `active`,
instead of settling the goal's status:

1. Write the `GoalPeriod` row (`outcome` from the existing `settleStatus`).
2. Advance the window in the same update: `startAt = old targetDate`,
   `targetDate = addPeriod(old targetDate, recurrence)`,
   `startValue = finalValue`, status stays `active`, `riskLevel`
   re-evaluated against the new window immediately.
3. `notify()` the goal's recipient (org-wide for org goals): "Q3 quota:
   achieved ✓" / "missed", link to the goal; `recordUserEvent('goal_achieved'
   | 'goal_off_track')` with `context.periodEnd`.

`addPeriod` is pure calendar math (`src/lib/goals/recurrence.ts`):
monthly/quarterly/yearly advance by calendar month(s)/year with end-of-month
clamping (Jan 31 + 1 month = Feb 28/29). If the process was down across
multiple boundaries, rollover loops until `targetDate > now`, writing one
`GoalPeriod` per elapsed window (later windows with no readings settle
`missed` with `finalValue = startValue`).

Non-recurring goals keep exact v1 settlement (status → `achieved`/`missed`).

## Prompt grounding

`src/lib/goals/grounding.ts`:

```ts
goalGroundingBlock(organizationId: string, userId?: string): Promise<string>
```

- Selects active goals visible to the context (org goals; plus `userId`'s
  personal goals when given), ranks `off_track > at_risk > no_data > on_track`
  then nearest deadline, takes 3.
- One line per goal: name, target + deadline, current value, risk phrase, gap
  vs pace. Header line: `Active goals (the user is working toward these):`.
  Hard cap ~600 chars; empty string when no goals — callers append only when
  non-empty.
- Wrapped in try/catch returning `''` on any error.

Injection points:

1. **Assistant chat** — appended to the existing grounding assembly in the
   assistant chat route (org + requesting user).
2. **Agent runs** — appended to the agent system prompt in the worker's
   execution path (org goals only; agent runs are not always user-scoped).
3. **Copilot / suggestion synthesis** — appended inside
   `buildCopilotGrounding` so flow copilot and the LLM synthesis paths see it.

## Weekly digest

`src/lib/goals/digest.ts`:

```ts
sendWeeklyGoalDigests(now?: Date): Promise<{ users: number; sent: number }>
```

- Cron leg in `/api/cron/dispatch`, Monday 14:00 UTC window (same shape as the
  weekly suggestion sweep; best-effort, never fails the tick).
- Per org with ≥ 1 active goal, per user: their visible goals — risk badge
  word, current vs pace values, week-over-week value delta (from datapoints),
  attributed runs in the last 7 days (contribution join), and any `GoalPeriod`
  settled in the last 7 days.
- Delivery per user: `notify()` (`type: 'goal.digest'`, level `info`, link
  `/goals`) + email via the built-in email integration when configured
  (subject "Your goals this week"; simple HTML list mirroring the notification
  content). Email failure logs and continues.
- Idempotence: atomic weekly claim on `users.metadata.lastGoalDigestAt`
  (exact pattern of `lastBehaviorSynthesisAt` in suggest-user-workflows) so a
  cron retry cannot double-send.
- Skips users with zero visible active goals.

## UI

- **Wizard step 1**: recurrence `Select` (One-time / Monthly / Quarterly /
  Yearly) with kind-based default.
- **Goal detail**: period-history rail above the chart — one chip per
  `GoalPeriod` (`Q1 ✓`, `Q2 ✗` styling via success/destructive tokens with ✓/✗
  glyphs, tooltip: final vs target); current window rendered as today.
  Quarter/month labels derived from `periodEnd`.
- **Goal card** (`/goals`): recurring goals show a small `↻ quarterly` hint in
  muted text.
- **Edit dialog**: target edits apply to the current window only (copy states
  this when the goal recurs).

## API

- `GET /api/goals/[id]` response gains `recurrence` and
  `periods: Array<{ periodStart, periodEnd, targetValue, finalValue, outcome }>`
  (newest first, cap 12).
- `POST /api/goals` accepts `recurrence` (validated enum, nullable).
- `PATCH /api/goals/[id]` accepts `recurrence` changes (applies to the current
  window's future settlement only).
- No new routes → no smoke-guard additions beyond existing cases re-passing.

## Error handling

- Rollover is transactional per goal (period write + window advance in one
  `$transaction`); a mid-loop crash resumes idempotently because the next
  evaluation re-detects `now > targetDate`.
- Grounding and digest are best-effort: empty block / logged skip, never a
  thrown error into a run or the tick.

## Testing

- Unit: `addPeriod` calendar math (month-end clamping, yearly, quarterly),
  multi-window catch-up rollover (2 missed quarters → 2 period rows), digest
  content assembly (pure formatter), grounding block ranking/cap/empty cases.
- e2e (extends `goals-e2e.test.ts`): recurring goal past its window →
  `GoalPeriod` written with correct outcome, window advanced, status still
  active; second run same clock → no duplicate period (idempotent); digest
  claim prevents double-send.

## Out of scope (v2.0)

- Per-period target ramps (each new window copies the previous target).
- Digest scheduling preferences (fixed weekly cadence).
- Grounding in Slack-bot sessions.
