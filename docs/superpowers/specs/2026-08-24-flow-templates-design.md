# Flow templates — save a flow you built, reuse it later

Date: 2026-08-24
Gap: #3 in `docs/parity/2026-08-24-backstory-flows-parity.md`
Status: proposed — not yet implemented

## The gap, stated precisely

The parity map called this "Sublime has literally no flow templates." That was
right about the symptom and wrong about the cause. Sublime has a great deal of
template machinery already:

- `AgentTemplate` is the single template model, org-owned, `configuration` JSON.
- `POST /api/templates/provision` materializes a template into real rows and
  **already accepts `targetKind: 'agent' | 'flow'`**.
- `POST /api/agent-templates` **already accepts `kind: 'agent' | 'flow'`**.
- `SEED_CATALOGUE` + 7 static `StarterTemplate`s render on the Flows page, and
  `flows/templates/[key]` is a working detail page.
- `provision-plan.ts` resolves connection slots and rewrites agent refs.

So the read/provision half exists and is good. The precise gap is two-sided:

1. **No write path.** Nothing anywhere creates a template from a flow —
   `grep -ri "save as template"` returns nothing. `AgentTemplate` rows come
   only from `POST /api/agent-templates` (hand-authored) and
   `template-from-run.ts` (intelligence-distilled).
2. **DB templates cannot carry a graph.** `loadDbTemplateRecipe` builds its
   `MaterializeSpec` from `config.instructions`. It never reads a graph. So a
   `kind: 'flow'` DB template today materializes a *single-agent* flow, not the
   authored multi-step topology. The column to hold a graph does not exist.

A user who builds a good five-step flow has no way to keep it.

## The blocker that shapes everything

**`AgentTemplate` is a public cross-org library by default.**

`GET /api/agent-templates` and `loadDbTemplateRecipe` both read via
`systemPrisma` with no organization filter. The only org-private templates are
those carrying `configuration.autoGenerated === true`, and that flag has a
specific existing meaning (distilled from an org's own runs).

So the obvious implementation — "save the flow as an `AgentTemplate` row" —
would **publish that flow's graph, step structure, prompts, and connection
names to every workspace on the platform.** For a feature whose entire purpose
is "keep my own work for reuse," that is the wrong default and a privacy
incident waiting to happen.

This is the single most important constraint in this document.

## Approach

**Chosen: extend `AgentTemplate`, do not add `FlowTemplate`.**

Backstory has a separate `FlowTemplate` + `FlowTemplateVersion` pair. Porting
that shape would give Sublime two template models, two catalogues, two
visibility rules, and a second provisioning path — while the existing one
already branches on `targetKind`. Backstory's model also carries
`catalogueStatus` review machinery tied to its `edition.config.ts`
internal/customer split, which Sublime has no concept of.

Rejected alternative: a `FlowTemplate` model mirroring Backstory. Cleaner
separation on paper, but it duplicates department taxonomy, integration
requirements, provisioning, and the catalogue UI — and every future template
feature would then need doing twice.

### 1. Visibility — the part that must be right

Add an explicit `configuration.visibility: 'org' | 'community'`.

Read paths resolve it as:

| stored value | who can read | why |
| --- | --- | --- |
| absent | every workspace | **backward compatibility.** Existing rows are public today; defaulting them to private would retroactively hide the community library. |
| `'community'` | every workspace | explicit publish |
| `'org'` | owning org only | the new default for anything saved from a flow |

`POST /api/flows/[id]/save-as-template` **always writes `'org'`**. Publishing
to the community library stays a separate, deliberate act, not a side effect of
saving your own work.

Both `GET /api/agent-templates` and `loadDbTemplateRecipe` gain the same
predicate. They must not drift — one shared helper,
`templateVisibleTo(config, viewerOrgId)`, mirroring how `nodeVisibleTo` is
shared between the two graph stores.

### 2. The graph must be sanitized, unconditionally

A template is read by other people and, once published, other workspaces. It
is an export in every meaningful sense.

Reuse `toPortableFlow` (`src/lib/export/portable.ts`) rather than writing a
second sanitizer. Its header already states the contract: sanitization is
unconditional, there is no opt-out, and it drops webhook secret hashes,
redacts `Authorization`/`Cookie`, redacts credential-shaped URL/query/body
values, and strips vault `credentialId`s and workspace-internal
`connectionId`s while preserving portable `nango:`/`native:`/`template:` ids.

That last property is exactly what a template needs: the portable ids resolve
to the *importing* workspace's own connections at provision time.

**A second sanitizer is the failure mode here.** One that drifts from the
export path would leak precisely the thing the export path learned not to.

### 3. Storage

No migration. `configuration` is already `Json?`:

```
configuration: {
  kind: 'flow',
  visibility: 'org',
  graph: <sanitized FlowGraph>,
  trigger: <normalized trigger, secrets dropped>,
  icon, integrations, requiredIntegrations, departments,  // existing keys
  savedFromFlowId: <id>,   // provenance, not a live reference
}
```

`savedFromFlowId` is provenance only. It must never be dereferenced at
provision time — the source flow may be deleted, edited, or belong to another
workspace by then. The stored graph is the template.

### 4. Provisioning reads the graph when present

`loadDbTemplateRecipe` gains one branch: when `kind === 'flow'` and
`config.graph` is a valid graph, carry it on the recipe and let the existing
flow-materialization path use it instead of synthesizing one from
`instructions`. Everything else — required-integration checks, connection
resolution, agent-ref rewriting, capacity limits, activation — is untouched.

When `config.graph` is absent or fails validation, fall back to today's
instructions-derived behaviour rather than erroring. An older template must
keep working.

### 5. UI

- **Save:** a "Save as template" item in the flow settings dropdown
  (`flows/[id]/page.tsx`), next to Duplicate / Download JSON. A small dialog
  for name, description, category, icon.
- **Use:** the Flows page already renders `TemplateCatalogueCard` for seeds.
  Saved templates render through the same card, in a "Your templates" group.
  No new design language — the UI is settled.

## Testing

Pure, unit-testable, no DB:
- `templateVisibleTo` — the full matrix, including absent-means-public.
- The graph round-trip: a graph with an inline credential, an `Authorization`
  header, a webhook secret and a vault `credentialId` comes back with all four
  gone and the `nango:`/`native:` ids intact.

DB-backed (`TEST_DATABASE_URL`):
- Saving a flow writes `visibility: 'org'`, and a second org's
  `GET /api/agent-templates` does not see it.
- A `'community'` template IS visible cross-org.
- An existing row with no `visibility` key stays visible cross-org.
- Provisioning a flow-kind template with a graph reproduces the step count and
  topology, not a single-agent flow.
- Provisioning a flow-kind template WITHOUT a graph still works (old rows).

## Explicitly out of scope

- Template versioning (`FlowTemplateVersion`). Sublime has `FlowVersion` for
  flows; templates can gain history later if it is actually wanted.
- Backstory's `catalogueStatus` review workflow — it belongs to an
  internal/customer edition split Sublime does not have.
- AI-generated templates (`source: 'ai_generated'`).
- Publishing UI for `'community'`. The value is supported and readable from
  day one; a deliberate publish flow is its own piece of work.
